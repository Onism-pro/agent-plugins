# 设计说明

## 问题

长会话里的记忆通常坏在三个地方，而且都很难察觉：

1. **越聊越慢越贵**。历史一直在上下文里堆着，每轮都要重发一遍；模型注意力被稀释，回答开始跑偏。
2. **记不清就是记不清**。用户说「我明明讲过」，没人能回答到底是没存、存了没用上、还是存错了。
3. **该忘的不会忘**。上周随口提的小事和生日一样权重，检索时互相挤。

这三件事没法用一句「加个记忆插件」解决，得分开做。

## 三层分工

```
原文日志      按天落盘，滚动保留          —— 底稿，用来对账
   │
对话压缩      老对话 → 一页摘要笔记        —— 控体积，保住发生过的
   │
审计          证据审计 / 遗忘体检          —— 回答「为什么忘了」
```

**为什么不直接删老对话？** 删了以后，「他说过的那件事」就只剩模型记忆里的一句模糊印象。压成笔记是从「逐字」降级到「梗概」，信息还在，代价可控，所以能读回来——如果笔记目录本身被别的插件索引，效果更好。

**为什么审计只报告不自动改？** 自动补记忆会把审计的结论当事实写回库，错了会自我强化。宁可每周出一张报告，人看一眼，再决定要不要手动补。

## 两个公式

压缩触发：`消息条数 ≥ trigger`（默认 90）时压到 `keep`（默认 50）。留够近因上下文，同时给笔记留出空间。

遗忘折算：

```
score = strength × 0.5 ^ (未提天数 / 半衰期)
半衰期：事件 7 天，其余 30 天
硬事实（生日、称呼、忌口、家人等）不参与
score < 2 且 未提 > 30 天 → 搬进归档表
```

归档不是删除：条目整行搬进 `memory_archive` 并标注原因，随时能搬回来。动作前自动备份数据库。

## 和参考项目的关系

分层、只追加、可审计这几条来自 [DeepSeek-memory-Ido1um](https://github.com/Ido1um/DeepSeek-memory-Ido1um) 的设计。没有直接采用它的实现，因为：

- 它是独立的 Node 引擎，接进 AstrBot 要写桥接层，等于两套记忆并行；
- 它的事实抽取是规则驱动的，只认说得很直白的句子；这里配合的记忆插件是模型抽取的，覆盖面更大。

所以这里只借它三件事：**原文留底**、**压缩不删除**、**审计只报告**。

## 边界

- 压缩有损。摘要保得住「发生过什么」，保不住原话；这也是原文日志存在的理由。
- 遗忘需要时间。数据不满一个月，基本上挑不出该淡出的条目。
- 表结构是外部约定的。记忆插件升级改字段，脚本可能失效，升级后先跑试运行。
